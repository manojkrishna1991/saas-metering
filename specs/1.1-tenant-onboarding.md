# Spec 1.1: Tenant Onboarding

Status: CONFIRMED, implemented
Module: `control-plane`

## 1. Goal
A SaaS platform admin can register a new tenant enterprise (e.g. "Globex Corp") so it can start using the platform's infrastructure.

## 2. Scope
In: `Tenant` entity, `TenantRepository`, `TenantService`, `POST /v1/tenants`, validation, error handling, tests.
Out: updating/suspending a tenant, listing/fetching tenants, plan/subscription assignment (see Story 1.2), auth.

## 3. Domain model

### Tenant
| Field | Type | Rules |
|---|---|---|
| id | UUID | PK, server-generated (`GenerationType.UUID`) |
| name | String | required, unique (case-insensitive), max 255 |
| status | enum | `ACTIVE`, `SUSPENDED`, `DEACTIVATED`; defaults to `ACTIVE` on registration |
| createdAt, updatedAt | Instant | auditing (`@CreatedDate`/`@LastModifiedDate`) |

## 4. API (JSON, base `/v1`)

| Method | Path | Purpose | Success |
|---|---|---|---|
| POST | `/tenants` | register a new tenant | 201, `Location: /v1/tenants/{id}` |

Request:
```json
{ "name": "Globex Corp" }
```

Response:
```json
{ "id": "...", "name": "Globex Corp", "status": "ACTIVE", "createdAt": "...", "updatedAt": "..." }
```

Errors use RFC 7807 `application/problem+json`:
- 400: blank/too-long `name`
- 409: a tenant with that name (case-insensitive) already exists

## 5. Layering
`TenantController` → `TenantService` → `TenantRepository`. The controller never touches the repository; the service owns the duplicate-name check and is the only class holding a `TenantRepository`.

## 6. Persistence
- PostgreSQL via Spring Data JPA, H2 for tests.
- Table `tenants`, unique constraint on `name`.

## 7. Acceptance criteria
1. `POST /v1/tenants {"name": "Globex Corp"}` → 201, body has `status: "ACTIVE"` and a generated `id`.
2. Registering the same name again (any case) → 409.
3. Blank or >255-char `name` → 400.
4. Unit tests cover the service (happy path + conflict); repository test covers the unique constraint; controller tests cover 201/400/409.

## 8. Assumptions confirmed with the user
- **Entity location:** `Tenant`/`TenantRepository` live in `control-plane` only, not `common-domain` — kept local to this module for now. If `ingestion-service` or `billing-worker` need to reference tenants later, this should move to `common-domain` at that point.
- **Primary key:** UUID, server-generated, not a sequential `Long`.
- **Status field:** included now (`ACTIVE`/`SUSPENDED`/`DEACTIVATED`) even though the story only exercises registration, since retrofitting it later would be costlier.

## 9. Note for Story 1.2 (package layout changed)
Story 1.2's spec (`specs/1.2-subscription-plan-assignment.md`, assumption A7) assumes the module skeleton stays on `com.example.demo`. That's no longer true: as part of this story the `control-plane` module was renamed from the Spring Initializr default `com.example.demo` to `com.saas.metering.controlplane` (matching the Gradle group `com.saas.metering` / artifactId `control-plane`), with `DemoApplication` → `ControlPlaneApplication`. New code in this module should use `com.saas.metering.controlplane.*`, e.g. `com.saas.metering.controlplane.tenant.Tenant`.

This also affects Story 1.2's assumption A1: `Tenant` now exists at `com.saas.metering.controlplane.tenant.Tenant` with primary key `UUID id`, so `Subscription.tenantId` can reference it directly instead of being a bare, unchecked UUID — worth reconciling before that story proceeds.
