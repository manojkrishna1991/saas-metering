# Spec 1.2: Subscription & Plan Assignment

Status: CONFIRMED, implemented
Module: `control-plane`, packages `com.saas.metering.controlplane.{plan,subscription,tenant}`

## 1. Goal
An admin can define billing plans (Free Tier, Pro Tier, ...) and assign one to an existing tenant. A plan carries included usage, an overage price and rate-limit threshold rules. The ingestion service and billing worker will read these later, but they are not built in this story.

## 2. Scope
In: `Plan`, `RateLimitRule`, `Subscription` entities, repositories, services, REST APIs, validation, error handling, seed data, tests, and two small additions to the Tenant code (§5).
Out: usage ingestion, enforcement of rate limits, invoice calculation, payment, authN/authZ, tenant update/list/get endpoints.

## 3. What Story 1.1 gives us (and the conventions this spec follows)
- `Tenant` is in `control-plane`: `UUID id`, `name`, `status` (`ACTIVE`/`SUSPENDED`/`DEACTIVATED`), auditing fields.
- Base path is `/v1`; the module package is `com.saas.metering.controlplane`.
- Layering is controller → service → repository. A service is the only class that holds its own repository, so Subscription code reaches tenants through `TenantService`, never `TenantRepository`.
- Errors are RFC 7807 `ProblemDetail`s from the single `web/GlobalExceptionHandler`.
- Entities use Lombok `@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder`, `@EntityListeners(AuditingEntityListener.class)` and `GenerationType.UUID`. Requests and responses are plain records; conversion lives in mapper classes (§10).
- Schema is created by Hibernate. Tests use H2 with `ddl-auto=create-drop`. There is no Flyway in the project and this story does not add it.
- Repository tests are `@DataJpaTest` with `@ContextConfiguration(classes = ControlPlaneApplication.class)`; controller tests use `spring-boot-webmvc-test`.

## 4. Domain model

### Plan (table `plans`)
| Field | Type | Rules |
|---|---|---|
| id | UUID | PK, server-generated |
| code | String | unique, immutable, `[A-Z0-9_]{2,32}`, e.g. `FREE`, `PRO` |
| name | String | required, max 255, e.g. "Pro Tier" |
| includedCalls | long | >= 0, per billing period |
| overagePricePaise | long | >= 0; ₹2/call is stored as 200 |
| currency | String | fixed `INR` for now |
| billingPeriod | enum | `MONTHLY` only for now |
| active | boolean | an inactive plan cannot be newly assigned |
| rateLimitRules | List<RateLimitRule> | 0..n, cascade all, orphan removal |
| createdAt, updatedAt | Instant | auditing |

Money is stored as integer paise, never as a float.

### RateLimitRule (table `rate_limit_rules`, owned by Plan)
| Field | Type | Rules |
|---|---|---|
| id | UUID | PK |
| type | enum | `REQUESTS_PER_WINDOW`, `USAGE_PERCENT_ALERT`, `HARD_CAP` |
| windowSeconds | Integer | required and > 0 for `REQUESTS_PER_WINDOW`; null otherwise |
| limit | Long | required and > 0 for `REQUESTS_PER_WINDOW`; null otherwise |
| thresholdPercent | Integer | required, 1..100, for `USAGE_PERCENT_ALERT`; null otherwise |
| action | enum | `THROTTLE` (429), `BLOCK`, `NOTIFY` |

- `REQUESTS_PER_WINDOW` is a burst limit, e.g. 100 calls per 60 s. Action is `THROTTLE` or `BLOCK`.
- `USAGE_PERCENT_ALERT` fires at x% of `includedCalls`. Action must be `NOTIFY`.
- `HARD_CAP` stops usage once `includedCalls` is reached, with action `BLOCK`. This is how Free Tier stops at its quota. A plan without a `HARD_CAP` keeps accepting calls and bills the overage.
- This story stores and validates the rules only. Enforcement comes later.

### Subscription (table `subscriptions`)
| Field | Type | Rules |
|---|---|---|
| id | UUID | PK, server-generated |
| tenant | ManyToOne Tenant | required, real FK to `tenants` |
| plan | ManyToOne Plan | required, real FK to `plans` |
| status | enum | `ACTIVE`, `CANCELLED` |
| startDate | Instant | set at creation |
| endDate | Instant | null while ACTIVE; set when cancelled or replaced |
| createdAt, updatedAt | Instant | auditing |

**Invariant:** a tenant has at most one `ACTIVE` subscription. H2 has no partial unique indexes, so this is enforced in the service. Assign and cancel first take a pessimistic write lock on the tenant row (`TenantService.getTenantForUpdate`), so concurrent requests for one tenant are serialised. Changing plan closes the current subscription (`CANCELLED`, `endDate=now`) and creates the new one in the same transaction, so history is kept.

## 5. Changes to Story 1.1 code
1. `TenantService` gains `getTenant(UUID)` and `getTenantForUpdate(UUID)`. Both throw `TenantNotFoundException`, a new exception handled as 404 in `GlobalExceptionHandler`. `TenantRepository` gains a `@Lock(PESSIMISTIC_WRITE)` `findById` variant for the update version.
2. `GlobalExceptionHandler` is extended with the new exceptions (§7). Validation errors keep the existing behaviour (first field error in `detail`).

No Tenant endpoints or fields change.

## 6. API (JSON, base `/v1`)

| Method | Path | Purpose | Success |
|---|---|---|---|
| POST | `/plans` | create plan with its rules | 201, `Location: /v1/plans/{id}` |
| GET | `/plans` | list plans (`?active=true` filter) | 200 |
| GET | `/plans/{id}` | get one plan | 200 |
| PUT | `/plans/{id}` | update name, includedCalls, overagePricePaise, active and rules (full replacement of rules). `code` is not changeable | 200 |
| POST | `/tenants/{tenantId}/subscription` | assign `{ "planCode": "PRO" }`. Creates a subscription, or switches plan if one is ACTIVE | 201, `Location: /v1/tenants/{tenantId}/subscription` |
| GET | `/tenants/{tenantId}/subscription` | current ACTIVE subscription with embedded plan and rules | 200 |
| GET | `/tenants/{tenantId}/subscriptions` | full history, newest first | 200 |
| DELETE | `/tenants/{tenantId}/subscription` | cancel the active subscription | 204 |

Example, create Pro Tier:
```json
POST /v1/plans
{ "code": "PRO", "name": "Pro Tier", "includedCalls": 50000,
  "overagePricePaise": 200, "currency": "INR", "billingPeriod": "MONTHLY", "active": true,
  "rateLimitRules": [
    { "type": "REQUESTS_PER_WINDOW", "windowSeconds": 60, "limit": 1000, "action": "THROTTLE" },
    { "type": "USAGE_PERCENT_ALERT", "thresholdPercent": 80, "action": "NOTIFY" }
  ] }
```

Subscription response:
```json
{ "id": "...", "tenantId": "...", "status": "ACTIVE", "startDate": "...", "endDate": null,
  "plan": { "id": "...", "code": "PRO", "name": "Pro Tier", "includedCalls": 50000,
            "overagePricePaise": 200, "currency": "INR", "rateLimitRules": [ ... ] } }
```

## 7. Errors (RFC 7807 `ProblemDetail`)
| Status | When |
|---|---|
| 400 | bean-validation failure (blank/over-long name, negative numbers, bad `code` pattern, unknown enum value, missing field) |
| 404 | tenant, plan or subscription not found, including an unknown `planCode` on assign and cancel with no active subscription |
| 409 | duplicate plan `code`; assigning the plan the tenant already has; assigning an inactive plan; assigning to a tenant whose status is not `ACTIVE` |
| 422 | rule combinations that are each valid but contradictory, see §8.3 |

## 8. Business rules
1. Plan `code` is unique and cannot change.
2. Subscriptions reference the plan row, so editing a plan changes the terms for current subscribers from then on. There is no per-subscription price snapshot (A4).
3. Rule validation, returned as 422:
   - at most one `HARD_CAP` per plan;
   - `USAGE_PERCENT_ALERT` thresholds are unique within a plan;
   - a plan with a `HARD_CAP` must have `overagePricePaise = 0`;
   - field/type pairing from §4 (e.g. `thresholdPercent` on a `HARD_CAP` rule), allowed actions per type.
4. Assigning the plan the tenant already has returns 409. A different plan performs an atomic switch (old CANCELLED with `endDate`, new ACTIVE).
5. Only `ACTIVE` tenants can be assigned a plan. Cancelling is allowed for any existing tenant.
6. There is no DELETE for plans. Plans are deactivated with `PUT`. Deactivating a plan does not touch existing subscriptions.

## 9. Seed data
Loaded on startup by an `ApplicationRunner` if the code is absent, idempotent, and skipped in tests unless a test inserts its own:
- `FREE` "Free Tier": 1,000 calls, overage 0, `HARD_CAP`, burst 60 per 60 s (`THROTTLE`), 80% alert.
- `PRO` "Pro Tier": 50,000 calls, 200 paise overage, burst 1000 per 60 s (`THROTTLE`), 80% alert.

(The Free figures are my proposal, see A3.)

## 10. Layering and package layout
Calls flow `Controller` → `Service` → `Repository`. `SubscriptionService` calls `PlanService` for plan lookup and `TenantService` for tenants, never another feature's repository.

Each feature package (`plan`, `subscription`, `tenant`) under `com.saas.metering.controlplane` uses the same sub-packages:

| Sub-package | Contents |
|---|---|
| `controller` | REST controllers (`PlanController`, `SubscriptionController`, `TenantController`) |
| `service` | business logic (`PlanService`, `SubscriptionService`, `TenantService`) |
| `repository` | Spring Data repositories |
| `entity` | JPA entities: `Plan`, `RateLimitRule`, `Subscription`, `Tenant` |
| `dto` | request and response records |
| `mapper` | static mapper classes: `PlanMapper`, `SubscriptionMapper`, `TenantMapper` |
| `exception` | feature exceptions, mapped to HTTP statuses in `web/GlobalExceptionHandler` |
| `utils` | enums (`BillingPeriod`, `RuleType`, `RuleAction`, `SubscriptionStatus`, `TenantStatus`) and `PlanSeedRunner` |

Shared pieces stay in `config/` (`JpaAuditingConfig`, `OpenApiConfig`) and `web/` (`GlobalExceptionHandler`). Tests mirror the main package structure; the end-to-end tests (`SubscriptionFlowIntegrationTest`, `OpenApiDocsTest`) sit at the module's test root.

## 11. Acceptance criteria
1. `POST /v1/plans` creates Free and Pro. Pro returns 50,000 included calls and 200 paise (₹2) overage.
2. `POST /v1/tenants/{id}/subscription {"planCode":"PRO"}` on a registered tenant returns 201, and `GET` returns the ACTIVE subscription with its rules.
3. Assigning `FREE` to a tenant already on `PRO` closes the PRO subscription and creates a FREE one. The history endpoint shows both, newest first.
4. Assigning the plan the tenant already has returns 409. An inactive plan returns 409. A non-ACTIVE tenant returns 409.
5. Unknown tenant, unknown `planCode`, or cancel with no active subscription returns 404.
6. Duplicate plan code returns 409. Invalid payloads return 400. Contradictory rules return 422.
7. Concurrent assigns for one tenant never leave two ACTIVE rows (service test with the lock, integration test with parallel requests on H2).
8. Seed data creates FREE and PRO once and is a no-op on the second run.
9. Tests: unit tests for `PlanService` and `SubscriptionService`; `@DataJpaTest` for repositories; MockMvc controller tests for every endpoint and status above; the existing Story 1.1 tests still pass.
